# GoVolley: рекомендации по устройству модулей

Дата анализа: 2026-10-19. Статус: предложения по рефакторингу; реализация не выполнена. Документ служит ориентиром для следующих изменений, а не утверждённым ADR или поручением выполнить все рекомендации за одну задачу.

Изучены основные сценарии профиля, входа, тренировок, общие контракты и соответствующие исходники тестов. Выводы получены чтением кода. Тесты, сборка, PostgreSQL integration и браузерные сценарии в рамках этого анализа не запускались. Перед реализацией сверяйте наблюдения с текущим кодом. Прежние результаты проверок относятся к датам, указанным в [истории проекта](../history/README.md).

## Принцип выбора изменений

Углубляйте модули: небольшой интерфейс должен скрывать значительное поведение. Интерфейс включает параметры, допустимые состояния, порядок вызовов, ошибки и необходимые настройки. Seam — место, в котором можно изменить поведение через интерфейс; adapter — конкретная реализация на этом месте. Проверяйте поведение через тот же интерфейс, которым пользуются вызывающие модули.

Вынос кода оправдан, если при удалении нового модуля правила и сложность возвращаются к вызывающему коду. Отдельный файл или проксирование вызова сами по себе глубины не добавляют. Вводите отдельный seam для зависимости при наличии конкретных производственного и тестового adapters либо другого реального различия реализаций.

## Порядок по архитектурной отдаче

1. Модуль редактирования профиля во frontend: черновик, обновление данных, аватар, сохранение и синхронизация сессии.
2. Модуль клиентского сценария входа через Telegram: инициализация, polling, истечение срока и отмена.
3. Общий контракт ответа с тренировкой: одна runtime-схема и производный TypeScript-тип.
4. Небольшое сопутствующее изменение: единые подписи уровней и отсутствующей локации во frontend.

Это порядок рефакторинга. Приоритет исправления действующих ошибок, особенно SPEC-001, определяется их влиянием на пользователей. Идентификаторы и критерии исправлений ведутся в [code-review-findings.md](code-review-findings.md); этот документ их не заменяет.

## 1. Редактирование профиля — первый кандидат

Исходники: [страница профиля](../../apps/frontend/app/profile/page.tsx), [шапка профиля](../../apps/frontend/app/profile/profile-header.tsx).

Страница координирует локальный профиль и профиль сессии, поля формы, выбранный файл, object URL, запросы при фокусе окна, multipart-сохранение и `update()` NextAuth. Шапка получает setters, DOM-событие выбора файла и ref. Вызывающий код должен знать порядок всех этих действий.

Риски, выведенные из исходников и требующие воспроизведения:

- Успешное обновление профиля при возврате фокуса заменяет черновик через эффект синхронизации, даже во время редактирования.
- «Отмена» меняет только `isEditing`: выбранные файл и предпросмотр сохраняются и могут попасть в последующее сохранение.
- Ранее запущенное чтение может завершиться после сохранения и заменить более свежий профиль.

Предлагаемый внешний seam — локальный hook `useProfileEditor()` в каталоге профиля. Пример интерфейса:

```ts
const { state, begin, change, cancel, save } = useProfileEditor();
// state различает загрузку, просмотр, редактирование и сохранение.
// Черновик и его предпросмотр принадлежат состоянию редактирования.
```

Имена иллюстративны. Цель — передавать намерения пользователя вместо согласования нескольких setters.

Правила и критерии готовности:

- `begin()` создаёт черновик из последнего принятого сохранённого профиля.
- Обновление серверных данных сохраняет активный черновик.
- `cancel()` сбрасывает несохранённые поля, выбранный файл и предпросмотр; object URL освобождается.
- `save()` отправляет снимок черновика; повторный запуск во время сохранения исключён.
- Устаревшее чтение не заменяет результат успешного сохранения.
- Ошибка синхронизации сессии после успешного сохранения отличается от ошибки записи профиля.
- Смена авторизованного пользователя очищает прежнее состояние и делает его незавершённые ответы неактуальными.

Ref файлового input держите внутри выбора аватара. Бронирования, видимость модального просмотра фото и подтверждение уровня остаются вне редактора. Сервер сохраняет полномочия по авторизации и проверке файлов.

Зависимости: собственный backend по HTTP, синхронизация NextAuth, фокус окна и object URL. При необходимости моделирования порядка ответов используйте внутренний seam транспорта с HTTP adapter и управляемым тестовым adapter в памяти. Подмену синхронизации сессии держите внутри тестовой настройки; страница не должна собирать эти зависимости вручную.

Проверяйте через интерфейс редактора: фокус во время редактирования, отмену аватара, запоздалое чтение после сохранения, ошибку записи, ошибку обновления сессии после успешной записи, смену пользователя и освобождение предпросмотра. Затем выполните относящиеся к изменению frontend-проверки и сценарий редактирования в интерфейсе.

## 2. Клиентский вход через Telegram

Исходники: [TelegramLogin](../../apps/frontend/components/auth/telegram-login.tsx), [AuthSessionService](../../apps/backend/src/auth/auth-session.service.ts).

Клиентский модуль сейчас объединяет отображение, инициализацию, два жизненных цикла AbortController, таймеры, проверку срока, интерпретацию статуса, вызов NextAuth и переход страницы.

Предлагаемый интерфейс — `useTelegramLogin()` с `{ state, start, cancel }`. Состояния могут быть `idle`, `starting`, `waiting`, `exchanging`, `failed`; в `waiting` доступна проверенная `botUrl` для ссылки открытия Telegram.

Реализация владеет таймерами, отменой запросов, игнорированием запоздалых ответов и единственной попыткой обмена в рамках одного запуска. После терминальной ошибки начинается новый вход. Отмена прекращает локальную работу; уже завершённый сервером обмен она не откатывает. Авторитетные TTL, подтверждение личности и однократное потребление сессии остаются на backend.

Для тестов используйте управляемый adapter собственного HTTP-транспорта, подмену NextAuth и времени/навигации на внутренних seams. Критерии: переход pending → confirmed, expired/consumed, ошибка завершения входа после подтверждения, отмена при инициализации и polling, размонтирование и поздний ответ предыдущего запуска. Существующие PostgreSQL и браузерные проверки сохраняют отдельное назначение.

## 3. Общий контракт ответа с тренировкой

Исходники: [shared-types/training.ts](../../packages/shared-types/src/training.ts), [frontend/lib/contracts.ts](../../apps/frontend/lib/contracts.ts).

TypeScript-интерфейс `Training` и runtime-схема ответа определены в разных местах. Frontend строит схему ответа из `CreateTrainingSchema` через `safeExtend`, заменяя отдельные поля. Это требует синхронизации определений и связывает чтение сохранённых записей с ограничениями создания. Здесь зафиксирован архитектурный риск, а не воспроизведённая новая ошибка валидации.

Предложение: экспортировать `TrainingResponseSchema` из `@govolley/shared-types`, выводить `Training` из неё и использовать схему в браузерных запросах и серверном рендеринге. Схемы create/update остаются отдельными; общие примитивы полей можно переиспользовать без переноса ограничений только для записи в ответ.

Зависимости — Zod и данные в процессе; дополнительный adapter не требуется. Критерии: реальные формы ответов backend принимаются схемой, nullable-поля и неверные типы проверяются, различие между пропущенным полем PATCH и явной очисткой сохраняется. Существующие проверки HTTP и SSR продолжают работать.

Вычисление `isBooked` остаётся в `TrainingService` с учётом текущего пользователя. Перенос схемы не закрывает SPEC-002: для него отдельно нужна передача пользователя в update/remove и формирование ответа.

## Сопутствующее изменение: подписи во frontend

STD-002 описывает расходящиеся названия уровней; SPEC-003 — отображение пустой локации. Используйте один `Record<SkillLevel, string>` для подписей и `locationLabel(value)` для null, пустой и пробельной строки. Примените их в карточке и форме тренировки, деталях, боковом блоке записи, статистике профиля и списке бронирований там, где показываются соответствующие значения.

Выберите единое название BEGINNER: сейчас используются «Начинающий» и «Новичок». Русские подписи принадлежат frontend. При нормализации текста в контрактах записи сохраните различие между отсутствующим полем PATCH и явной очисткой; отображение должно учитывать уже сохранённые пустые строки. Готовность и закрытие STD-002/SPEC-003 проверяются по исходным записям замечаний.

## Существующие seams, которые стоит сохранить

- **TrainingService:** запись, отмена, изменение вместимости и мягкое удаление используют общий протокол row lock PostgreSQL. Сохраняйте правила в одном модуле; SPEC-002 исправляется передачей личности в формирование ответа, без распределения протокола блокировки.
- **AuthSessionService:** TTL, первая подтверждённая личность, атомарное потребление и откат при ошибке подписи сосредоточены вместе. Исправление SPEC-001 сохраняет `telegramId` как идентичность и устойчивость входа к коллизиям username.
- **AvatarStorage / UsersService:** файловые ключи и операции принадлежат хранилищу; порядок записи БД и очистки файлов — обновлению профиля. Сохраняйте это разделение и существующие проверки наблюдаемого результата.
- **evaluateLevel:** небольшой интерфейс скрывает валидацию, сумму и пороги; дополнительный интерфейс стратегии пока не обоснован.
- **trainingApi:** скрывает от браузерных вызывающих модулей адреса, сериализацию и схемы. Общую абстракцию транспорта для SSR и браузера вводите при конкретном повторении поведения, которое она устранит.

## Выполнение и фиксация результата

Для первой задачи достаточно редактора профиля и проверок его интерфейса. Сценарий входа и контракт ответа можно выполнять независимо после оценки текущего кода. Задачи и их статусы ведите по [правилам трекера](issue-tracker.md).

Тесты внутренних деталей заменяйте проверками того же наблюдаемого поведения через новый интерфейс. Сохраняйте проверки уникальных гарантий PostgreSQL, multipart и браузера: тест adapter в памяти их не заменяет. После реализации отдельно зафиксируйте внесённые изменения, реально выполненные проверки и оставшиеся ограничения в истории. Статусы STD-xxx/SPEC-xxx обновляйте после выполнения их критериев готовности.
