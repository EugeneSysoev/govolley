# GoVolley MVP: план разработки для агентов

Статус: процесс реализации согласован владельцем 19 октября 2026 года; выполнение задач этим документом не подтверждается. План объединяет выбор навыков и работу подагентов в отдельных worktree с одним итоговым PR. Запрос на изменение документации выполняется как работа с документацией; полный процесс запускается по явному поручению реализовать MVP.

## Источники и область работы

- Продуктовые требования и 25 сценариев приёмки: [спецификация MVP](../MVP-SPEC.md) и [GitHub issue #1](https://github.com/EugeneSysoev/govolley/issues/1).
- Реализация: задачи [#2–#15](https://github.com/EugeneSysoev/govolley/issues), их критерии и нативные зависимости. Перед запуском перечитай актуальные тела, комментарии и блокировки по [правилам трекера](issue-tracker.md); таблица ниже — согласованный снимок плана.
- Термины и решения: [доменная документация](domain.md), корневой CONTEXT.md и применимые ADR. Устройство затрагиваемых модулей сверяй с [рекомендациями](codebase-design.md).
- Открытые STD/SPEC и прежние результаты: [замечания](code-review-findings.md) и [история](../history/README.md). Прежние успешные проверки сохраняют свою дату.

Цель полного запуска — реализовать #2–#15 в одной интеграционной ветке и одном PR. #14 — сопутствующее исправление STD-001: оно не блокирует продуктовую приёмку #15, но входит в полный согласованный набор изменений PR.

## Навыки и роли

| Когда | Навык и действие |
| --- | --- |
| Координация всего MVP | implement-spec: прочитать граф, создать общую ветку и draft PR, выдавать доступные задачи, собирать результат и завершить общий PR. |
| Выполнение одной задачи | implement: реализовать критерии, применять tdd на согласованных seams, регулярно проверять типы и целевые тесты, выполнить проверки задачи и сохранить коммиты в её ветке. |
| Новый проверяемый сценарий | tdd: один падающий тест → минимальная реализация → следующий сценарий. Ожидания брать из спецификации; проверять наблюдаемое поведение через согласованный interface. |
| Выбор или изменение interface модуля | codebase-design: небольшой interface скрывает правила; сохранять их в одном модуле, создавать adapter при реальном различии зависимостей. Это справочник при проектировании. |
| Ошибка или регрессия | diagnosing-bugs: сначала воспроизводимый сигнал конкретной ошибки, затем причина, исправление и регрессионная проверка. |
| Уточнение доменных состояний | domain-modeling: согласовать терминологию, сохранить модель в CONTEXT.md либо решение в ADR; продуктовые правила сверять со спецификацией. |
| Конфликт при интеграции | resolving-merge-conflicts: выяснить намерения обеих задач, сохранить согласованное поведение, выполнить проверки и завершить интеграцию. |
| Завершение задачи и всего PR | code-review: два независимых подагента Standards и Spec; сохранить разделение отчётов, устранить замечания и проверить исправления. |
| Дополнительная проверка интерфейса | computer-use: проверить пользовательский путь в браузере; автоматические HTTP/PostgreSQL и браузерные проверки остаются основой приёмки. |

Читай SKILL.md выбранного навыка перед применением, а дополнительные references — по потребности. На текущем компьютере пользовательские навыки доступны в C:/Users/User/.agents/skills/<имя>/SKILL.md, а computer-use предоставляется установленным плагином; в другом окружении используй его каталог навыков. Определения implement-spec и implement предоставлены владельцем для этого процесса.

## Порядок полного запуска

### 1. Подтвердить исходное состояние

Прочитай актуальные инструкции, спецификацию и задачи. Проверь git status и историю: baseline 479a127b6827c62599ce08dcb0839b2df5fa11dd сохраняет исходники, тесты и документы, включая прежние незакоммиченные изменения, на которых основана спецификация. Следующий cd98178808e2ffa0d2e10121f91a6e3707fe1ea0 добавил ссылки задач в замечания ревью.

Исходной точкой общей ветки служит актуальный локальный main, содержащий baseline. Проверь достижимость baseline в его истории и учти появившиеся изменения владельца. Удалённая основная ветка может отставать: инструментам создания worktree передавай явный локальный ref/commit, включающий нужную историю.

Готовность шага: сохранены исходный SHA общей ветки, статус рабочего дерева, актуальный граф и выбранная целевая ветка будущего PR; пользовательские изменения учтены.

### 2. Открыть общую ветку и draft PR

Создай интеграционную ветку от подтверждённого состояния и один draft PR в согласованный репозиторий. Обеспечь доступность нужной истории в head-ветке PR. Если PR включает ранее локальный baseline, явно отрази это в описании и учти его в фактическом diff относительно целевой ветки.

Свяжи PR с #1 и задачами #2–#15; closing-ссылки должны соответствовать реально заявленному объёму. Статусы реализации и результаты проверок обновляй по правилам трекера.

Готовность шага: зафиксированы head/base PR, ссылка PR, SHA начала реализации и ссылки на требования. Создание PR не означает выполнение критериев задач.

### 3. Выдать доступный фронт подагентам

Выбирай задачи, чьи блокировки уже реализованы, слиты в общую ветку и проверены. Для исходного графа это #2, #3, #7 и независимо #14; выбирай из них по фактическому состоянию. При общем PR открытая до его слияния issue может уже иметь принятый результат в интеграционной ветке: фиксируй это ссылкой на коммиты и проверки. Одного сообщения исполнителя «готово» для снятия блокировки недостаточно.

Запускай не более двух исполнителей одновременно. Каждому дай отдельные worktree и ветку от зафиксированного текущего SHA общей ветки. Зависимые задачи получают состояние после интеграции блокировок. Сообщение исполнителю содержит указатели на issue, спецификацию, инструкции, task_base_sha, worktree и ожидаемый результат; исследовательские заметки при необходимости сохраняются вне репозитория в доступном всем участникам рабочем каталоге.

Учитывай общий лимит подагентов: в текущем сеансе доступны четыре активных агента вместе с координатором. Два исполнителя оставляют один слот интегратору; для code-review освобождай два слота под проверяющих. При другом лимите уменьши параллельность.

Согласуй владение изменениями общей Prisma-схемы, shared-контрактов, зависимостей и lockfile. Изолируй локальные тестовые БД, порты серверов и временные файлы каждого исполнителя. Общую тестовую БД под конкурирующие миграции не используй.

Готовность выдачи: задача действительно доступна, worktree содержит нужные коммиты, сохранён task_base_sha, определены ресурсы проверок и свободные слоты.

### 4. Реализовать и проверить отдельную задачу

Исполнитель использует implement, навыки из таблицы и критерии своей issue. В tdd записывает выбранные уже согласованные seams, запускает проверку в состоянии red, вносит минимальное изменение и подтверждает green. При чистом prefactoring сначала фиксирует существующее проверяемое поведение и сохраняет его после изменения; исправление ошибки получает собственную регрессию.

Запускай целевые тесты и typecheck по ходу работы. В конце задачи выполни относящиеся интеграционные и браузерные проверки, обязательные lint и сборку, а полный существующий набор тестов — один раз после завершения изменений. Коммиты сохраняются в выделенной ветке задачи.

Ревью задачи использует явный task_base_sha: git diff <task_base_sha>...HEAD и git log <task_base_sha>..HEAD --oneline. Передай Spec-проверяющему issue задачи и применимые требования #1; Standards-проверяющему — инструкции проекта. Code-review выполняется двумя независимыми подагентами. Устрани замечания и повтори проверки затронутого поведения; для повторного ревью передавай актуальный HEAD и первоначальную базу задачи.

Готовность задачи: каждый критерий подтверждён результатом, проверки и ограничения записаны, оба отчёта ревью обработаны, перечислены коммиты, миграции и необходимые действия интегратору. Исторические результаты не заменяют новые.

### 5. Интегрировать результат

Подагент-интегратор последовательно сливает проверенные ветки задач в общую ветку. Для конфликтов применяет resolving-merge-conflicts и учитывает требования обеих задач. Совместимость миграций проверяет на объединённой истории, включая обновление базы со старыми записями.

После слияния проверь затронутые сценарии и совместимость контрактов. При конфликте или изменении результата слияния повтори необходимые проверки и ревью изменённой части. Сохраняй общий SHA, результат проверок и принятые задачи; только затем пересчитывай фронт и выдавай следующие.

Готовность интеграции: коммиты присутствуют в общей ветке, согласованные проверки затронутого поведения прошли, зависимости новых задач действительно доступны.

### 6. Завершить общий PR

Выполни #15 на собранной ветке и подтверди все 25 сценариев. #14 можно закончить независимо от этой продуктовой приёмки; готовность полного PR по #2–#15 включает и его критерии.

Запусти code-review всего фактического diff PR относительно зафиксированной базы целевой ветки; проверка только последней задачи не заменяет общее ревью. Отдельно учитывай границу начала MVP-реализации и включённый baseline. Сохрани отчёты Standards и Spec раздельно. Замечания общего ревью исправляет один implementer-подагент; повторные проверки и ревью соответствуют внесённым исправлениям.

Обнови описание PR по итоговому объёму, приведи closing-ссылки в соответствие с выполненными задачами, запиши фактические проверки и ограничения в истории. После приёмки и ревью переведи PR из draft в ready for review. Автоматическое слияние PR в main в этот план не входит.

Заверши работу с созданными worktree после проверки достижимости всех нужных коммитов в общей ветке и сохранности незакоммиченных результатов. Для управляемых worktree используй штатное архивирование.

Готовность полного запуска: один PR с реализованным согласованным объёмом, проверенные критерии задач и #15, обработанные Standards/Spec, записанные ограничения и сохранённая история.

## Уже согласованные проверки

Testing Decisions и полный список сценариев находятся в [спецификации](../MVP-SPEC.md#testing-decisions). Для этих seams повторное подтверждение владельца не требуется:

- Основные действия — внешний HTTP API с настоящей отдельной тестовой PostgreSQL; проверяются пользовательский результат и сохраняемое состояние. Подмена БД и проверки внутренних вызовов не заменяют доказательство конкурентной целостности.
- Браузерные сценарии — реальные frontend/backend и тестовая PostgreSQL; fixture заменяет внешнее подтверждение Telegram. Автоматический браузерный набор дополняется проверкой через computer-use при необходимости.
- Уведомления — контролируемый adapter Telegram с ошибками, повторами и перезапуском доставки.
- Время управляется для точных границ 3 часов и дня 90/91 по Пхукету; сценарии будущих записей проверяются до первого использования пакета.
- Совместимые миграции проверяются на пустой и заполненной legacy-данными тестовой базе; текущие команды typecheck, lint, build и тестов берутся из package.json и README.
- Доступность живого бота, реальная доставка, внешние тайлы карты и production проверяются отдельно с сохранением ограничений. Production-деплой, изменение production-секретов и миграция рабочей БД не входят в этот запуск разработки.

Если потребуется seam за пределами уже согласованных, отдельно сформулируй его и согласуй до добавления тестов на нём. Результаты отмечай фактическими командами и исходами; STD/SPEC закрываются только после проверки собственных критериев.
