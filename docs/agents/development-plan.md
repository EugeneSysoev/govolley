# GoVolley MVP: процесс реализации

Обновлено по поручению владельца 21 октября 2026 года: сократить избыточные проверки и передачу контекста, сохранив требования и доказательства. Эта редакция заменяет прежний порядок подэтапов и общие рекомендации навыков, когда они требуют лишних повторов. Изменение процесса не подтверждает готовность MVP.

## Старт и источники

1. Прочитайте [RESUME.md](RESUME.md): текущее состояние и следующий шаг. Проверьте бюджет по разделу «Лимит» до запуска исполнителей.
2. Координатор один раз читает [PROJECT.md](../PROJECT.md), затем [MVP-SPEC.md](../MVP-SPEC.md). Через [GitHub tracker](issue-tracker.md) сверяет тела, комментарии и зависимости актуального фронта; полный граф обновляет при старте и его изменении.
3. Проверьте git status, worktree и SHA. Продолжайте существующие codex/govolley-mvp и [draft PR #16](https://github.com/EugeneSysoev/govolley/pull/16). Исходный SHA реализации: f685aa55f1e8e340401d9f582bf8beef35c3f6e5, содержащий baseline 479a127b6827c62599ce08dcb0839b2df5fa11dd. Сохраняйте последующие изменения.

Готовность старта: известны актуальный статус, доступный фронт и бюджет. Запрос на документы изменяет документы; реализация запускается отдельным поручением.

## Контекст и роли

- Максимум два исполнителя одновременно. Каждый работает в отдельной ветке/worktree от явного актуального SHA интеграционной ветки после проверенной интеграции блокировок. Незавершённый worktree продолжают с сохранением исходного task_base_sha.
- Новые подагенты по умолчанию получают fork_turns="none". Поручение: issue, применимые разделы спецификации/инструкций, worktree, ветка, task_base_sha, владение общими файлами и тестовые ресурсы. Полную историю передают только при конкретной потере контекста, которую нельзя устранить указателем; причина записывается.
- Исполнитель читает свою issue и указанные разделы. Прочитанные неизменённые материалы повторно не загружаются. Важное решение сразу сохраняется в файл задачи, чтобы продолжение не зависело от памяти агента.
- Prisma-схема, shared-контракты, lockfile и общая инфраструктура имеют назначенного владельца на параллельный этап. БД, порты и временные файлы изолированы. Изменение interface передаётся другому исполнителю ссылкой на контракт/коммит.
- Простое слияние выполняет координатор. Интегратор нужен для содержательного конфликта, сложной миграции или другой оправданной изоляции. Исследователь получает конкретное неизвестное и сохраняет краткую записку.
- Исполнители сами не создают reviewer-подагентов. Координатор назначает ревью завершённых изменений и контролирует активные слоты.
- Шаблон поручения: «issue + применимые критерии; policy_source и SHA; task_base_sha; ветка/worktree; владение файлами; тестовые БД/порты; ожидаемые коммит и отчёт». Ответ исполнителя: SHA, выполненные критерии, команды/результаты, оставшееся и шаг интеграции. Остальные подробности передаются ссылками.
- Поиск: сначала rg/список имён, затем нужный участок. Вывод инструментов — необходимые поля, diff и итог; полные логи остаются файлами. Обрезанный большой вывод заменяется узким запросом. Метаданные инструментов выбираются по подходящим именам.
- Агент сообщает о результате, препятствии или изменении interface. Координатор ждёт штатным инструментом; ожидание не требует повторного чтения неизменившихся status/log. Пользовательские обновления содержат новые факты.

## Реализация и проверки

Применяйте implement, tdd и профильный навык из таблицы. SKILL.md выбранного навыка читается один раз; текущие указания владельца имеют приоритет. Согласованные seams из MVP-SPEC повторно подтверждать не нужно.

| Момент / изменение | Достаточная проверка |
| --- | --- |
| Новый сценарий или ошибка | Один red → минимальная реализация → green через согласованный interface. Существующий воспроизводимый red заново не доказывают. |
| Рабочий срез | Целевой тест; typecheck затронутого workspace после изменения interface или завершённого среза. |
| Готовность задачи к интеграции | Критерии issue, целевые регрессии, typecheck/lint затронутых workspace и потребителей контракта, необходимая production-сборка — один раз на итоговом состоянии. |
| HTTP/учёт/права/гонки | Относящиеся HTTP + настоящая отдельная PostgreSQL: состояние, повторы, конкуренция и права. Подмена БД не заменяет эти гарантии. |
| UI/время/вход | Относящиеся component/browser-сценарии с настоящими frontend/backend/PostgreSQL. Общий smoke повторяется, когда затронут его путь или инфраструктура. |
| Миграция | Пустая и заполненная legacy тестовые БД; сохранность данных и объединённая история миграций. |
| Простое слияние без изменения проверенного результата | Состав коммитов и совместимость. Результаты исполнителя переиспользуются с исходными SHA/датой; связанные параллельные изменения получают целевую совместную проверку. |
| Конфликт / содержательное исправление | Изменённое поведение и затронутые потребители; расширять набор при конкретном риске или регрессии. |
| Итоговая #15 | Полный набор на собранном PR: typecheck, lint, build, unit/component, HTTP/PostgreSQL, browser, миграции и все 25 сценариев. |

Полный монорепозиторный suite не является отдельным ритуалом каждой задачи или подэтапа. Команды выбираются из package.json/README. Успешная проверка хранит команду, SHA/состояние, окружение и результат. Повтор нужен из-за изменения входов/зависимостей/поведения, сбоя либо недоказанного критерия; пауза и новый чат сами по себе результат не отменяют. После малого исправления повторяют затронутую проверку. После итогового ревью весь набор повторяют только при системных изменениях, делающих прежний результат неприменимым.

## Ревью и интеграция

- Исполнитель передаёт коммит и компактный отчёт: критерии → доказательства, проверки, ограничения, миграции и подсказки интеграции. Координатор сверяет diff и полноту доказательств; каждый подэтап не порождает отдельный обзор.
- Независимый code-review выполняется двумя осями Standards и Spec для завершённого вертикального этапа/пакета задач и обязательно всего итогового PR. Пакетный обзор перечисляет task_base_sha, проверяемые HEAD и покрытые задачи. Отдельное промежуточное ревью назначается по конкретному риску; календарные правила, авторизация и учёт проверяются содержательно до зависимого использования.
- Дефекты и нарушения требований/обязательных правил исправляются с регрессией. Оценочный smell/P3 не запускает рефакторинг автоматически: описать конкретный риск и решить «исправить сейчас» либо «отложить с основанием». Явный критерий issue и согласованные STD/SPEC этим решением не отменяются.
- Исправление проверяет автор замечания по изменённой части. Обе оси заново проходят весь diff только при широком изменении, затрагивающем их обе. Малая правка или документация не перезапускает реализацию, два ревью и сборки с начала.
- Зависимая задача стартует после слияния блокировок и проверки затронутых гарантий; назначенное риском ревью должно быть завершено. Различайте «реализовано», «слито, проверка ожидается» и «принято». Для закрытия issue/STD/SPEC нужны доказательства критериев, одного merge-коммита недостаточно.
- Координатор сохраняет принятый SHA и обновляет RESUME. Исторические отчёты остаются снимками. Интеграционная запись ссылается на существующие результаты вместо их полного копирования.

## Лимит: остановка на 50%

Порог — абсолютный usedPercent общей квоты аккаунта в окне windowDurationMins=300, а не прирост на 50 пунктов от старта. Проверять через get_usage_limits при старте, перед новым исполнителем/широкой приёмкой и после этапа. При нескольких bucket выбрать применимый к текущей работе и записать его ID. Это не точный счётчик токенов этой задачи.

Каждый исполнитель также проверяет квоту при старте, после законченного среза и перед длительной группой проверок. При 40% сообщает координатору; при 45% сохраняет checkpoint и завершает turn. Контроль не должен зависеть только от активности координатора, пока подагенты работают.

- **Ниже 40%:** выполнять доступный фронт с запасом на завершение и запись.
- **От 40%:** закончить текущий ограниченный этап; новые задачи и расширение scope отложить.
- **От 45%:** прекратить выдачу работы, сохранить результаты и завершить активных агентов; подготовить checkpoint и остановиться с запасом к 50%.
- **50% и выше при старте или следующем измерении:** реализацию не начинать/не продолжать. Только безопасное сохранение состояния и завершение запуска. Сброса автоматически не ждать, reset/кредиты без поручения владельца не использовать.

Если датчик недоступен, сохранить этот факт и состояние; реализация ждёт достоверного измерения. Другие чаты делят квоту, поэтому резерв обязателен: точный останов на 50.00% не гарантируется. При скачке за порог прекратить работу исполнителей на безопасной границе, сохранить незавершённые файлы без объявления готовности.

## Передача и завершение

Перед паузой обновить [RESUME.md](RESUME.md): ветки/worktree/SHA/dirty, принятые задачи, невыполненные проверки, точный следующий шаг, ресурсы, доказательства и бюджет. Незавершённую реализацию сохранить отдельным WIP-коммитом своей ветки, когда безопасно; если коммит не получился, явно перечислить dirty-файлы. Worktree сохранить. Секреты остаются в игнорируемой локальной конфигурации. Итоговое сообщение содержит ссылку на RESUME и факт остановки.

Полное завершение: #2–#15 приняты, все 25 сценариев #15 подтверждены, две оси ревью фактического diff PR относительно зафиксированной целевой базы обработаны, описание/closing-ссылки и ограничения актуальны. Затем PR переводится в ready for review. Слияние в main и production не входят в поручение. Worktree очищаются после проверки сохранности результатов; управляемые архивируются штатным инструментом.
