# Первый администратор и управление тренерами

Владелец сначала входит в GoVolley через Telegram. Для назначения нужен числовой Telegram ID именно этого аккаунта, проверенный владельцем; изменяемый username для назначения не используется.

В доверенном окружении сервера после установки зависимостей и применения миграций задайте `DATABASE_URL` нужного окружения и `ADMIN_TELEGRAM_ID` владельца. Из корня репозитория выполните:

```powershell
$env:ADMIN_TELEGRAM_ID = '123456789' # замените на проверенный ID владельца
bun run admin:bootstrap
Remove-Item Env:ADMIN_TELEGRAM_ID
```

`DATABASE_URL` передаётся через окружение процесса. Если он хранится в защищённом файле, можно явно загрузить его: `node --env-file=apps/backend/.env scripts/bootstrap-admin.mjs`. Команда не загружает `.env` автоматически.

Команда меняет ровно одну уже существующую запись по уникальному `telegramId`, выводит ID аккаунта GoVolley и допускает повторный запуск для того же аккаунта. Пустой, некорректный или неизвестный Telegram ID завершает команду с ошибкой; новые пользователи не создаются. Отсутствие аккаунта означает, что нужно сначала завершить Telegram-вход и проверить ID. Настройка не назначает всех пользователей администраторами и не выполняется при запуске публичного приложения. Выполнение в production остаётся явной операцией владельца; разработка и тесты используют отдельную локальную тестовую БД.

После назначения обновите профиль. Администратор видит ссылку «Управление тренерами» и может найти конкретного пользователя по ID, имени или username. Поиск по цифровому ID — точный; текстовый поиск показывает первые 50 совпадений. Кнопки назначают `COACH` или возвращают `USER`; результат сохраняется и отображается на странице. Роль `ADMIN` этим интерфейсом и HTTP-сценарием не выдаётся и не снимается.

HTTP: `GET /api/users/role-candidates?q=...` и `PATCH /api/users/:id/role` с телом `{"role":"COACH"}` или `{"role":"USER"}`. Оба запроса требуют JWT и актуальную роль `ADMIN`. Обычный профиль продолжает отвергать служебные поля. На каждом защищённом запросе JWT проверяется вместе с ролью из БД, поэтому снятый тренер теряет полномочия со старым токеном.

Проверка настройки и доступа: `TEST_DATABASE_URL` отдельной локальной базы с окончанием `_test`, затем `bun run test:db:prepare` и `bun run --cwd apps/backend test:integration --runTestsByPath test/roles.postgres-spec.ts`. Проверка вызывает настоящую команду назначения, подтверждает результат через HTTP, повторяет её и проверяет, что другой аккаунт остался `USER`.
