## Архитектура и поведение

Контроллеры проверяют HTTP-ввод, авторизацию и роли; сервисы задают бизнес-правила и транзакционные границы.
JwtStrategy загружает актуального пользователя из БД на каждом защищённом запросе: роль из старого JWT не даёт сохранённых привилегий.
В модели нет владельца тренировки, поэтому дополнительное ограничение владения не придумано: COACH и ADMIN управляют расписанием согласно существующему интерфейсу.

Бронирование, отмена, изменение лимита и мягкое удаление используют одну блокировку строки PostgreSQL.
Повторная запись уже записанного пользователя и повторная отмена идемпотентны; CANCELLED можно восстановить при наличии места.
Лимит нельзя уменьшить ниже числа существующих CONFIRMED.
Существующие брони после мягкого удаления сохраняются для просмотра/отмены; новая запись запрещена.
Проверки подтвердили и вместимость, и ожидаемые конфликты, а не только отсутствие исключений.
Прямые ручные SQL-изменения должны соблюдать тот же протокол; триггер, защищающий произвольные обходные записи, не вводился.

Auth-ссылка действует 10 минут от создания для PENDING и CONFIRMED.
Подтверждение атомарно закрепляет первую Telegram-личность; обмен атомарно переводит CONFIRMED в CONSUMED.
JWT сохраняет прежний срок 30 дней. Ошибка подписания откатывает потребление.
Если после успешного обмена потерян HTTP-ответ или не создана NextAuth cookie, требуется новый вход: повторная выдача по sessionId запрещена.
Очистка всех старых состояний согласована с TTL и не является условием безопасности.
Polling не делает перекрывающихся запросов, прекращается при терминальном статусе/ошибке и очищает ресурсы при отмене.
Клиентское обновление сессии не может назначить роль, уровень или подтверждение; профиль перечитывается с backend.

AvatarStorage работает только с созданными сервером UUID-ключами и проверяет нормализованный путь, realpath и тип файла.
Новый файл сохраняется до транзакции БД; прежний удаляется после commit. При отказе БД новый файл очищается, если БД подтверждает отсутствие ссылок.
При неоднозначном commit или недоступной БД очистка откладывается, чтобы не удалить актуальный файл.
Legacy image допускается только как безопасный публичный URL известного формата; никогда не становится ключом удаления.
Произвольные и потенциально опасные legacy-значения не возвращаются в публичный профиль.

Общие схемы отделяют DTO от модели хранения и JSON response. isBooked относится к текущему пользователю, currentParticipants считает CONFIRMED.
Nullable location/price/description/coachName отражены в типах. Browser client и серверный транспорт разделены.
Общий пакет собирается в dist; удалены устаревшие сгенерированные JS из src, дублирование и небезопасные any в затронутых местах.
Восстановление lint потребовало небольших исправлений прежнего мёртвого кода и типов компонентов; массовое форматирование frontend не выполнялось.

## Миграция и действия при развёртывании

Подготовлена только новая миграция `apps/backend/prisma/migrations/20261018000000_avatar_key/migration.sql`:
добавляет nullable User.avatarKey, без переноса недоверенного image в ключ удаления.
Уже существующие миграции не менялись.

1. Установить зависимости по bun.lock рабочим Node/Bun.
2. Согласовать env по новым примерам: серверный BACKEND_URL без /api, NEXTAUTH_URL, общий серверный NEXTAUTH_SECRET, backend DATABASE_URL/TELEGRAM_BOT_TOKEN.
   Старые NEXT_PUBLIC_API_URL/NEXT_PUBLIC_BACKEND_URL больше не управляют API.
3. Применить новую миграцию штатной процедурой prisma migrate deploy до запуска нового backend; подготовить резервную копию по принятой процедуре эксплуатации.
4. Собрать и выпустить backend/frontend совместно: протокол онбординга теперь передаёт answers, а auth-сессия одноразовая.
5. Не удалять старые аватары по значениям image. Очистка legacy/отложенных файлов требует отдельной сверки с БД.
6. Проверить прежние журналы на credentials БД и bearer JWT/accessToken. При подтверждённой утечке владелец окружения решает ротацию/отзыв токенов.
   Доказательств фактической публикации журналов не получено; опасное логирование в старых исходниках подтверждено.

## Зависимости и ограничения

D1 проверен по [официальному advisory Next.js](https://github.com/vercel/next.js/security/advisories/GHSA-p293-qw3h-jr36):
затронут Windows-хостинг; конкретный патч начинается с 16.3.3. Установлена более новая совместимая 16.4.2 и выполнен повторный аудит.
D2 проверен по [официальному advisory Multer](https://github.com/expressjs/multer/security/advisories/GHSA-wc9g-mqfw-jrwm):
исправление начинается с 2.3.0; фактически используется 2.4.0 в прямой и NestJS-зависимости.
NextAuth обновлён до 4.24.15, Prisma — до 7.10.1. NestJS остаётся в ветке 11, без перехода на Nest 12.
Остальные обновления были адресованы результатам аудита в совместимых semver-диапазонах; audit fix --force и массовый latest не применялись.

Финальный аудит сохранён в `dependency-audit.json` рядом с этим отчётом:

- **maplibre-gl**, critical, внутри MapTiler SDK. [Официальный advisory](https://github.com/maplibre/maplibre-gl-js/security/advisories/GHSA-jrc7-96c5-q579)
  описывает вставку стороннего attribution HTML; исправленная major-ветка начинается с 6.4.1, тогда как совместимый SDK закрепляет ветку 5.
  Создание уязвимого attribution control отключено, вместо него статические React-ссылки. Конфигурация и сохранение STREETS проверены компонентным тестом.
  Библиотечный advisory остаётся открытым: изменение карты в будущем не должно возвращать HTML control до совместимого исправленного обновления.
  Живые тайлы/WebGL с настоящим MapTiler key не проверялись.
- **braces**, high, цепочка micromatch → ts-loader / frontend lint. Проект не передаёт в эти инструменты недоверенные сетевые glob-шаблоны.
  Совместимого исправления текущего дерева не получено; риск касается инструментов разработки, а не доказанного HTTP-сценария приложения.
- **sprintf-js**, moderate, цепочка coverage/Jest → js-yaml 3 → argparse. Недоверенные format strings от HTTP туда не передаются.
  Осталось в транзитивном инструментарии; принудительный несовместимый override не вводился.

Нерешённых вопросов по обязательным бизнес-правилам нет: пороги 15/18 утверждены пользователем, а роли и судьба существующих броней сохранены по текущей модели.
Остаются действия эксплуатации (env/миграция/возможная ротация), живые внешние интеграции и сопровождение трёх отмеченных зависимостей.
Полностью чистый аудит и проверка production-окружения не заявляются.
