## Результат

- Отдельная операторская команда `bun run admin:bootstrap` читает `ADMIN_TELEGRAM_ID` и `DATABASE_URL` из окружения. Параметризованный запрос назначает ADMIN ровно одной существующей учётной записи с уникальным Telegram ID. Некорректный/пустой ID и неизвестный аккаунт завершаются ошибкой. Повтор команды допустим; остальные аккаунты сохраняют роли. Команда не запускается публичным сервером. Реальная production-БД и секреты не использовались. [Инструкция](../../admin-setup.md) содержит воспроизводимый порядок настройки и проверки.
- `GET /api/users/role-candidates?q=...` доступен только ADMIN и возвращает ограниченный список аккаунтов (ID, имя, фамилия, username, роль; максимум 50). Цифровой ID ищется точно, текст — по имени/username без учёта регистра.
- `PATCH /api/users/:id/role` принимает только `USER` и `COACH`, защищён JWT и ADMIN guard. Условное изменение исключает ADMIN из целей и защищает от гонки с первоначальной настройкой. Нельзя ни выдать ADMIN, ни снять его через этот HTTP-сценарий. Несуществующий ID даёт 404, некорректный/выходящий за диапазон PostgreSQL Int — 400. Профиль сохраняет строгий запрет служебных полей.
- Существующий JwtStrategy уже читает актуальную роль из PostgreSQL на каждом защищённом запросе; он сохранён. Тесты подтверждают потерю полномочий после снятия COACH со старым токеном, включая токен с прежним `role: COACH` claim.
- `/admin/coaches` доступен из профиля ADMIN, позволяет найти конкретный аккаунт, назначить/снять тренера и показывает сохранённый результат. USER/COACH видят отказ при прямом переходе; список и кнопки скрыты. Доступ к данным страницы привязан к текущему access token, чтобы результаты прежней сессии не показывались после смены аккаунта.
- Prisma schema, миграции, зависимости и lockfile не менялись. Отдельные StaffRolesController/Service ограничивают пересечение с последующей работой над учениками.

4. ID за пределами PostgreSQL Int: сначала 500/P2020 для `2147483648`; после ограничения схемы — 400 для всех неверных ID.
