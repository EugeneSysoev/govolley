# Issue #3 — Telegram-вход при коллизии username

Дата: 2026-10-19. Задача: [#3](https://github.com/EugeneSysoev/govolley/issues/3), замечание SPEC-001, сценарий MVP 24. База задачи: `f685aa55f1e8e340401d9f582bf8beef35c3f6e5`. Этот отчёт фиксирует реализацию и проверки; независимое Standards/Spec-ревью выполняет координатор общего PR.

## Реализация

`AuthSessionService.confirm` сохраняет идентичность по `telegramId`. При конфликте уникальности с Telegram username исходная транзакция откатывается полностью, затем подтверждение один раз повторяется без записи username. Новый пользователь получает nullable username; существующий сохраняет прежнее значение. Профиль владельца занятого username не изменяется. Повторная транзакция заново проверяет одноразовый claim и общий TTL. Уровень, проверка уровня и роль не перезаписываются данными Telegram. Схема Prisma и миграции не изменялись.

## Диагностика и TDD

Согласованный seam — настоящий HTTP API и отдельная локальная PostgreSQL с реальными уникальными ограничениями. Подменено только внешнее подтверждение Telegram, вызывающее тот же `AuthSessionService.confirm`, что и бот.

Команда воспроизведения: `bun run --cwd apps/backend test:integration --runTestsByPath test/auth-collision.postgres-spec.ts` с `TEST_DATABASE_URL` выделенной БД. До исправления: `PrismaClientKnownRequestError: Unique constraint failed on the constraint: User_username_key` при подтверждении сессии после успешного `PATCH /api/users/profile` другого пользователя. Начальная fixture с недопустимым именем была исправлена до подтверждения воспроизведения; рабочий repro использует валидное имя длиной менее 30 символов.

Проверены гипотезы: конфликт независимого уникального username при upsert по telegramId подтверждён PostgreSQL; невалидный профиль исключён успешным HTTP PATCH; истёкшая/потреблённая сессия исключена HTTP polling `pending`. Минимальный сценарий red до изменения реализации, green после него. Вторая регрессия проверяет смену владельца username у существующего ученика с ADVANCED и подтверждённым уровнем, запрет повторного подтверждения и десять конкурентных HTTP-обменов (один успех, девять 401). Временное диагностическое логирование не добавлялось.
